# Booking slot capacity rollout gate

Admin rescheduling stays disabled unless both `ENABLE_BOOKING_SLOT_RESERVATIONS=true` and `BOOKING_SLOT_RESERVATIONS_READY=true` are set. The backend also checks that the unique `BookingSlotReservation.bookingId` index exists before it advertises scheduling as enabled or accepts a reservation.

Do not set the readiness flag until the business owner has supplied authoritative, garage-specific capacity for each supported date/time slot and an isolated, reviewed reconciliation has created reservation rows for every active booking with a schedule. Each capacity row's `reservedCount` must match the authoritative active booking set. Existing booking schedules are intentionally not inferred into capacity or changed by application startup.

Capacity records are keyed by the deterministic `_id` returned by `services/bookingSlotReservations.capacityId(dealerId, scheduleDate, timeSlot)`. `scheduleDate` is `YYYY-MM-DD`; `timeSlot` must match the booking's supported slot label. Before advertising rescheduling, the API checks the booking's current slot against authoritative booking counts and configured capacity. During an approved schedule change, the transaction conditionally increments a slot only while `reservedCount < capacity`, releases the booking's previous reservation, and writes the booking, consumed consent and audit event together. A missing reservation row can be repaired only for the exact source/target slot when the authoritative active booking IDs, existing reservation rows and `reservedCount` agree; any orphan, counter mismatch, missing capacity, unique-index issue or transaction failure blocks the operation. This is an on-demand transactional repair, not a startup or bulk backfill.

There is no default capacity and no automatic backfill. Keep both flags unset until capacity and reservation reconciliation are independently reviewed. Enabling the flags is an operational deployment decision and is not part of this code change.
